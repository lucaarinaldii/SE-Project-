# Решения по модульному дизайну: View Equipment

Рабочие решения для занятия Software Engineering 1, неделя «Modular Design and Software Construction».
Это не код и не отчёт шага 8. Файл нужен, чтобы сверить решения с use case и диаграммой классов.

Use case: **View Equipment** (просмотр каталога станков).
Проект: Campus Makerspace Management System.
Аутентификацию как основной use case не берём. Она остаётся только предусловием.

Источники:

- текст use case 5, View Equipment;
- диаграмма классов (`User`, `Student`, `Equipment`, подклассы, отдельный класс `Ticket`);
- sequence diagram для этого use case в репозитории нет. Порядок шагов взят из текста use case.

Шаг 5 записан ниже. Код шага 6 есть в двух местах: отдельный проект `view-equipment` и тот же каталог внутри `course_registration_portal`. Шаги 7–8 ещё не сделаны.

## Шаги 1–2. Какие классы и методы закрывают сценарий

### Что на диаграмме относим к этому use case

- `Equipment`: пять полей — `ID`, `Type`, `Location`, `Max_Booking_Duration`, `Min_Threshold`.
- Методы `Equipment`: `Get_Status()`, `Is_Open()`, `Get_N_Instruments(Type)`, `Check_Availability()`, `Is_Low()`.
- Подклассы: `3D Printer`, `Cutter`, `Elec Work`, `Printer`.
- У подклассов есть `Get_Plastic()` и `Get_Ink()`.
- `Ticket` — отдельный класс. К станку он относится связью через `Equipment_ID`, это не поле `Equipment`.
- `Reserve()` и `Cancel()` — методы `Student`, не `Equipment`.
- Предусловие «пользователь вошёл» закрывает включённый use case Authentication: `User.Authenticate(Password)`.

### Решение по шагам сценария

1. Открыть каталог. Отдельного класса «каталог» нет. `Get_N_Instruments(Type)` возвращает число станков типа, а не список. Список станков на диаграмме не закрыт.
2. Показать тип, место и текущий статус. Тип и место — поля `Type` и `Location`. Статус — `Get_Status()` или `Is_Open()`. Оба возвращают да/нет, не слово «открыт» или «заблокирован». В списке статус обязателен: так написан шаг 2 use case.
3. Выбрать станок. Отдельного метода нет. Это один `Equipment` по `ID`.
4. Показать описание, правила пользования и статус. Статус снова `Get_Status()` / `Is_Open()`. Описания и полного текста правил на диаграмме нет. В правилах пользования показываем `Max_Booking_Duration`: это единственное поле диаграммы про правила. Полным текстом правил оно не является.
5. Перейти к свободным слотам или к брони. Это уже другие use case: `Equipment.Check_Availability()` и `Student.Reserve()`. В модули просмотра каталога их не включаем.

Фильтр в use case называет 3D-принтер, лазерный резак и электронику. На диаграмме этому близки подклассы `3D Printer`, `Cutter` и `Elec Work`. Подкласс `Printer` в тексте фильтра не назван. Это пробел между use case и диаграммой, не наше правило. `Get_N_Instruments(Type)` для фильтра недостаточен: он отдаёт количество, не список.

Если ничего не найдено, сценарий показывает «No equipment found». Отдельного метода для этого сообщения нет.

Если станок заблокирован, сценарий требует пометку Blocked, причину и срок. `Is_Open()` может сказать, что станок закрыт. Причины и срока на диаграмме нет.

### Что сознательно не относим к View Equipment

- `Student.Reserve()`, `Student.Cancel()` — бронь и отмена. В каталог не входят.
- `Is_Low()`, `Min_Threshold` — склад.
- `Get_Plastic()`, `Get_Ink()` — уровень материала, сценарий этого не просит.
- `Check_Availability()` — переход в Track Availability.
- Класс `Ticket` — заявки о поломке. Поле станка из него не делаем.
- Остальные методы студента и менеджера: история и аккаунты.

## Шаг 3. Модули

Пять модулей. У каждого одна работа, одно предложение.

1. **Страница каталога.** Показывает каталог станков. Прячет экран и формат запроса. Другие модули её не вызывают.
2. **Каталог.** Описывает станки мейкерспейса. Прячет подклассы, чтобы новый тип станка не менял страницу.
3. **Статус.** Говорит, можно ли сейчас пользоваться станком. Прячет два булевых метода диаграммы, `Get_Status()` и `Is_Open()`.
4. **Хранилище.** Отдаёт сохранённые записи станков. Прячет, файл это или база. Каталог и статус сами файл не читают.
5. **Вход.** Отвечает, есть ли сессия у этого запроса. Прячет пароль, число ошибок и способ входа. Для этого use case это только предусловие.

## Шаг 4. Что оставляем после проверки

Те же пять модулей. Внутри каждого functional cohesion: элементы модуля делают одну работу. Между модулями не тянем чужие поля.

1. Страница не читает файл и не вызывает `Get_Status()` или `Is_Open()`. Иначе это content coupling: страница лезет в чужие данные. Она передаёт только нужные значения. Это data coupling: запрос во вход, тип в каталог, id в статус.
2. Каталог не включает причину блокировки, свободные слоты, уровень пластика или чернил и порог склада. Иначе cohesion каталога падает.
3. Подкласс станка знает только каталог. Хранилище отдаёт поле `Type`, а не классы `3D Printer`, `Cutter`, `Elec Work`, `Printer`.
4. Статус наружу отдаёт один результат: открыт или заблокирован, а при блокировке ещё причину и срок. Два флажка диаграммы наружу не выходят.
5. Списку станков не нужны пароль и id студента. Каталог для вошедших пользователей общий. Чью сессию проверять, страница передаёт во вход вместе с запросом. Общего глобального входа нет: это был бы common coupling.
6. Запись, которую каталог читает из хранилища, не содержит заявку и `Min_Threshold`. `Ticket` — отдельный класс со связью `Equipment_ID`, не поле станка. Иначе правка жалоб или склада меняет просмотр каталога.
7. Хранилище отдаёт каталогу целую запись станка (id, тип, место, лимит брони, описание). Это stamp coupling: передаётся структура, а не одно значение. Принимаем его на этой границе, потому что каталогу нужны несколько полей одной и той же записи. Страница эту запись не видит. До страницы доходят только значения её контрактов.

Проверки сменой одного решения:

- «Да/нет» заменяется на «Blocked + причина + срок». Меняется модуль статуса. Страница, каталог и хранилище остаются.
- Файл заменяется базой данных. Меняется только хранилище.
- Пароль заменяется университетским входом (на слайде стейкхолдеров это single university login). Меняется только вход.

## Шаг 5. Контракты между модулями

Страница каталога вызывает вход, каталог и статус. Каталог и статус вызывают хранилище. Страница хранилище не вызывает.

Список use case обязан показывать текущий статус. Каталог статус не отдаёт. Страница один раз вызывает `listEquipment(type)`, затем один раз `statusOf(ids)` с id из этого списка и сама соединяет строки. Цикл `machineStatus(id)` по каждому станку запрещён. Карточка одного выбранного станка вызывает `machineStatus(id)`.

Пустой список — не ошибка: страница сама показывает «No equipment found».

Описания, полного текста правил, причины и срока на диаграмме классов нет. В контрактах эти поля уже есть. Пока описания нет, текст приходит пустым. Это не ошибка. Правила пользования пока заполняются из `Max_Booking_Duration`. Причина и срок приходят из `readStoredStatus`, если они сохранены.

### Страница просит вход

`currentSession(request)`

- Принимает: текущий запрос. Пароль и id студента не передаются.
- Возвращает: у этого запроса сессия есть.
- Отказ: `NoSession`. Каталог в этом случае не открывается.
- Обещание: в ответе нет пароля, числа ошибок и способа входа. Функция не читает глобальную сессию.

### Страница просит каталог

`listEquipment(type)`

- Принимает: тип или пустое значение, если нужны все станки. Допустимые типы фильтра: 3D-принтер, лазерный резак, электроника.
- Возвращает: список из id, типа и места.
- Отказ: `UnknownType`, если тип не из этого списка. `StorageUnavailable`. Пустой результат — успешный ответ.
- Обещание: в элементах каталога нет статуса. Статус списка страница берёт отдельным вызовом `statusOf(ids)`. Нет слотов, чернил, пластика, порога склада и заявки. Подклассы наружу не выходят. То, что `Printer` не входит в фильтр use case, хотя на диаграмме такой подкласс есть, — пробел между документами, не правило. В общем списке такой станок виден.

`equipmentDetails(id)`

- Принимает: id станка.
- Возвращает: id, тип, место, описание, правила пользования.
- Отказ: `EquipmentNotFound`, `StorageUnavailable`.
- Обещание: правила пользования сейчас собраны из `Max_Booking_Duration`. В ответе нет причины блокировки, слотов, уровня материала, порога склада и заявки.

### Страница просит статус

`statusOf(ids)`

- Принимает: список id станков, которые только что вернул `listEquipment`.
- Возвращает: для каждого id «открыт» либо «заблокирован» вместе с причиной и сроком.
- Отказ: `EquipmentNotFound`, если какого-то id нет. `StorageUnavailable`.
- Обещание: один вызов на весь список. Причина и срок есть только у заблокированного станка. `Get_Status()` и `Is_Open()` в ответе нет.

`machineStatus(id)`

- Принимает: id выбранного станка.
- Возвращает: «открыт» либо «заблокирован» вместе с причиной и сроком.
- Отказ: `EquipmentNotFound`, `StorageUnavailable`.
- Обещание: то же, что у `statusOf`, но для одной карточки. Для строк списка этот вызов не используется.

### Каталог просит хранилище

`listMachineRecords()`

- Принимает: ничего. Фильтр по типу хранилище не делает.
- Возвращает: записи с id, полем `Type`, местом, `Max_Booking_Duration` и описанием.
- Отказ: `StorageUnavailable`.
- Обещание: это поле `Type`, а не классы подтипов. В записи нет статуса, заявки и `Min_Threshold`. Заявка живёт в классе `Ticket`.

`findMachineRecord(id)`

- Принимает: id станка.
- Возвращает: одну такую же запись.
- Отказ: `EquipmentNotFound`, `StorageUnavailable`.
- Обещание: то же, что у списка записей.

### Статус просит хранилище

`readStoredStatus(id)`

- Принимает: id станка.
- Возвращает: сохранённое значение статуса и, если они есть, причину и срок.
- Отказ: `EquipmentNotFound`, `StorageUnavailable`.
- Обещание: хранилище не решает, что такое «заблокирован». Это решает модуль статуса. Два флажка диаграммы остаются внутри него. Каталог этот вызов не использует.
